Always-Active Functions (Execute on Every Host)

display_fake_gui()
● ALWAYS EXECUTES
Renders a NEXUS-branded window with a progress bar labelled "Synchronising ceremony-controller..." Completes after 45 seconds and displays a success message. This is the social engineering layer — it makes the victim believe the tool is working while the real payload operates in the background.
steal_session_token()
● ALWAYS EXECUTES
Extracts authentication tokens from the user's browser session storage and Windows DPAPI credential store. Targets NEXUS portal cookies, OAuth tokens, and any cached service account tokens. This is the function that captured KABIR's session token — the token later replayed from Amsterdam (Room 7).
beacon_c2()
● ALWAYS EXECUTES
Establishes a persistent connection to c2.parallax-sys.net using XOR-encrypted HTTP POST requests. Beacons every 300 seconds (±45s jitter). Sends stolen tokens and system information to the C2 server. Receives tasking commands (e.g., "deploy to target X"). This is the beacon traffic captured in Room 3's PCAP.
install_persistence()
● ALWAYS EXECUTES
Creates a Windows scheduled task named "NexusHealthMonitor" that executes the payload every 5 minutes. Also adds a Run registry key for boot persistence. The scheduled task is the same process identified in Room 4 (PID 2847 on AETHER-7).

⚡ The Activation Condition Explained
The propagation module is guarded by a single environment variable check: NEXUS_ZONE. This variable is set automatically on all hosts that are part of the NEXUS core infrastructure zone. Developer workstations, volunteer laptops, and external machines do not have this variable set.

On KABIR's laptop: NEXUS_ZONE is not set → the function reaches .dormant_exit → propagation does not activate. The malware quietly steals tokens and beacons, but does not spread.

On AETHER-7: NEXUS_ZONE=CORE → the function reaches mira_propagate() → propagation activates. The worm begins enumerating services, harvesting tokens, cloning identities, and deploying copies across the NEXUS infrastructure.

Dormant Propagation Module — mira_propagate()

enum_services()
◆ CONDITIONAL — Only on NEXUS_ZONE=CORE
Queries the NEXUS service registry API to discover all connected services, their endpoints, trust relationships, and authentication methods. Uses the nexus-svc-continuity identity to authenticate. Returns a list of peer services that accept implicit trust connections.
harvest_tokens()
◆ CONDITIONAL — Only on NEXUS_ZONE=CORE
Extracts inter-service authentication tokens from the host's credential store. On NEXUS core hosts, these tokens are stored in a shared memory segment for performance. The function reads them directly — no password cracking, no brute force. Just reading what the system makes available to any process in the core zone.
clone_identity()
◆ CONDITIONAL — Only on NEXUS_ZONE=CORE
Creates a new service identity by combining harvested tokens with the forged aether-core.nexus.internal certificate (obtained via Room 5's certificate renewal exploit). The cloned identity is indistinguishable from a legitimate NEXUS service. This is how MIRA-7 became invisible.
deploy_to_peers()
◆ CONDITIONAL — Only on NEXUS_ZONE=CORE
Copies the malware payload to peer services using the implicit trust relationships identified in Room 6. Each copy inherits the same propagation logic — if the destination host is also in the CORE zone, the new copy will also begin propagating. This is the self-replicating mechanism that makes MIRA-7 a worm.
register_as_nexus()
◆ CONDITIONAL — Only on NEXUS_ZONE=CORE
Registers the deployed copy as a legitimate NEXUS service in the scheduler. The registered service appears in the NEXUS service dashboard, responds to health checks, and participates in the ceremony automation workflow. It is functionally indistinguishable from a real service — because it uses real credentials, real certificates, and real trust relationships.

⚠ Key Finding — The Worm Was Designed to Wait
MIRA-7's propagation module was not a bug or an unfinished feature. It was deliberately designed to remain dormant until the malware reached the NEXUS core infrastructure. This is a staged deployment strategy:

Stage 1 (KABIR's laptop): Quiet data theft. Steal tokens, establish C2 communication, maintain persistence. Do not attract attention.
Stage 2 (AETHER-7): Full activation. Enumerate services, harvest credentials, clone identities, deploy copies, register as legitimate services. Become part of the infrastructure.

The dormant branch is the reason the malware was not detected on KABIR's machine. It behaved like a simple information stealer — suspicious, but not catastrophic. The worm only revealed its true nature when it reached the environment it was designed for.

⚠ The dormant branch is mira_propagate(), guarded by the condition NEXUS_ZONE == "CORE". On KABIR's laptop (no NEXUS_ZONE), propagation stayed dormant. On AETHER-7 (NEXUS_ZONE=CORE), the worm activated and began spreading.
